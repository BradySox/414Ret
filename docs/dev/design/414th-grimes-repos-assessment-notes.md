# Grimes (mrSkortch) — repository assessment

Assessed 2026-08-20. Grimes is the author of MIST and SLmod and the maintainer of the
Hoggit scripting wiki. He owns 7 GitHub repositories at
[github.com/mrSkortch](https://github.com/mrSkortch). This note records what is in each
one, what the fork can use, and what it must not.

**Verdict: one repository is worth acting on.** `DCS-miscScripts` carries a live in-game
dump of every DCS object's sensor and weapon data, plus a standalone IADS script with a
hand-built SAM database. Everything else is either already retired here, already ours, or
dead.

This repo is **LGPL-3.0**. GPL-3 code cannot be pulled into an LGPL-3 distribution without
relicensing the whole tree, and a repo with no licence file grants nothing at all.

The practical rule: **use his data to check our numbers, never to populate them.** A measured
value read out of DCS is a fact and a fact is not his to license; his compiled files are.
If we ever want a file wholesale, ask him — he is reachable and has answered questions in
public for a decade.

**Already handled by accident.** Retiring MIST (2026-07-10, `414th-mist-moose-shim-notes.md`)
deleted the only GPL-3 file in the tree. That was done for maintenance reasons; it was also
the right licence call.

**Tidied 2026-08-20.** `resources/plugins/base/mist_moose_shim.lua` described itself as
"replicated verbatim" from MIST in six places, and its design note in one more. API
compatibility was never the concern; the wording was. All seven now describe the observable
contract the shim satisfies — MIST's documented call signatures and return shapes — rather than
derivation from a GPL-3 source. No behaviour changed.

## 3. ObjectDB2 — a second ground truth for unit data

`DCS-miscScripts/ObjectDB2/everyObject.lua` is a 1.5 MB Lua table holding **625 DCS objects**,
each with `getDesc()`, `getSensors()` and `getAmmo()` as the running sim reports them. It is
generated by `ObjectDB/writeDBScript.lua`, which walks `mist.DBs.unitsByName` in a dump
mission and writes one file per object plus the merged table.

`ObjectDB2/attributeList.lua` is the same set indexed by DCS **attribute** — 113 keys including
`SAM SR`, `SAM TR`, `SAM CC`, `SAM LL`, `LR SAM`, `MR SAM`, `SR SAM`, `EWR`, `AAA`, `Jammer`,
`Datalink`, `RADAR_BAND1_FOR_ARM`.

`ObjectDB2/sourceList.lua` indexes the same set by the module that supplies each unit.

### Why this matters here

Our unit data comes from one path: the wiki's `pydcs_export.lua` run against a DCS install,
diffed by `tools/verify_mod_export.py`. That path needs a DCS box, a hand-patched exporter and
one launch. Grimes' dump is a **different API path** (`getSensors()` at runtime, not the
mission-editor database) and is already published.

It matters because the two paths disagree, and the disagreement runs the wrong way for us:

| Unit | Grimes `getSensors()` headOn (m) | Grimes' own IADS `max_range_finding_target` (m) |
|---|---|---|
| S-300PS 64H6E sr ("Big Bird") | **80,249** | 160,000 |
| S-300PS 40B6MD sr | 80,249 | 60,000 |
| SA-11 Buk SR 9S18M1 | **66,874** | 100,000 |
| S-300PS 40B6M tr | 106,998 | 160,000 |
| 1L13 EWR | 200,622 | — |
| 55G6 EWR | 267,496 | — |
| Patriot str | 173,872 | — |
| Hawk sr | 60,187 | — |
| Dog Ear radar | 23,406 | — |

The 64H6E row is the one to chase. Its sensor block reports `typeName = "S-300PS 40B6MD sr"`
and the 40B6MD's exact range — so in the running sim the Big Bird detects at ~80 km, not the
160 km its database entry advertises. Grimes hand-copied 160,000 into his IADS from the DCS
`scripts/database` files; the runtime API is what actually governs a mission.

**Open item, needs the local checkout (pydcs is not installed in the CI container).** Compare
`AirDefence.S_300PS_64H6E_sr.detection_range` and the Buk SR against the table above. If pydcs
carries 160 km, then every detection ring we draw for an S-300 search radar overstates by 2×,
and the player is being told to stand off twice as far as the sim requires. Same check for the
Buk SR. This is the same class of defect as the `IranFAC_MG_AShM` 14× inflation caught on
2026-07-20 — a database field standing in for a sensor field.

**Second use — closure on PR #887.** Ramius007 closed the Dog Ear carve saying an EWR gives the
same benefit at far greater range. Measured: Dog Ear 23.4 km, 1L13 EWR 200.6 km. He was right by
a factor of nine. Do not re-open that carve.

**Third use — missile envelopes we do not model.** Each launcher's `getAmmo()` entry carries the
missile's real envelope, not just a range. The SA-11's 9M38M1 reports `rangeMin = 3000`,
`altMin = 22`, `altMax = 22000`, `rangeMaxAltMin = 25000`, `Nmax = 19`. We model a threat as a
flat circle of `threat_range`. A floor, a ceiling and a minimum range are all sitting in this
data. Not proposed as work — recorded because the data exists and the question ("can we model
a SAM's altitude floor?") will be asked eventually.

**Coverage limit.** His dump is his install: vanilla DCS + the WW2 pack + the 23 ED-integrated
`CHAP_*` units. No HDS, no VWV, no Iran pack, none of our other extensions. It covers the units
our layouts and preset groups mostly use, and nothing our mod packs add.

## 4. IADScript — what it has that MANTIS does not

`DCS-miscScripts/IADScript/script_iads_dev.lua`, v36, ~105 KB, standalone (needs MIST).

Its first ~720 lines are a hand-curated `samTypesDB` covering **24 systems** — S-300, Buk, S-125,
Kub, Patriot, Hawk as `complex`; Roland, Tunguska, Osa, Strela-10M3/-1, Tor, Gepard, Igla,
Linebacker, Chaparral, Vulcan, Avenger, Stinger, Shilka as `single`; 1L13, 55G6, Dog Ear and the
Roland radar as `ewr`. Every system lists its search radars, tracking radars and launchers with
detection range, altitude band, radar rotation period, missiles per launcher and rearm time.

Three ideas here are genuinely absent from our MANTIS bridge:

1. **`radarSim` — detection gated on the radar sweep.** A search radar only sees you when its
   antenna is pointed at you. Grimes tracks `radar_rotation_period` per radar (64H6E: 12 s over
   2 sides = 6 s; Buk SR: 12 s) and polls on the shortest one in the network. MANTIS polls a flat
   `detectInterval` (15 s here). This is a fidelity idea with a real player consequence — a fast
   low pass between sweeps.
2. **SAM magazines with rearm.** 18 launchers carry `missiles` counts (S-300 4, Buk 4, Kub 3,
   Patriot 4, Hawk 3, Tor 8, Tunguska 8, Osa 6, Avenger 8, Stinger/Igla 3) and `rearmTime`
   (23 s for a Shilka-class reload up to 1800 s for an S-300), some with `rearmPer` for partial
   reloads. His `rearm` setting sources them from placed warehouses, airbase ownership or
   logistics. **We have magazines for ships (§81) and cruise missiles (§63) and nothing for SAMs.**
   A SAM belt that can be shot dry, and that rearms along the same supply lines §90 already
   models and the depots §56 already makes bombable, is a coherent fork feature. It is also the
   answer to "why does saturating a site achieve nothing".
3. **Four ROE states with parent/child hand-off** — `dark`, `search`, `fireAtWill`, `auto`,
   propagated down a parent/child tree inside a named network. Comparable in spirit to what
   MANTIS gives us, but explicit and inspectable, and it writes `iads_list.lua` / `iadTargets.lua`
   for debugging.

**Corroboration of a hard constraint.** `script_iads_dev.lua` calls `enableEmission` **zero**
times. It manages radar state entirely through ROE and tasking, exactly as our constraint
requires (§51, §63, §77, the C-130 script). The most experienced IADS scripter in DCS reached
the same conclusion independently. Do not re-litigate that constraint.

**Not a MANTIS replacement.** MANTIS is bundled in MOOSE, is the sole engine here by decision
(`414th-mantis-iads-HANDOFF.md`), and our bridge already carries point defence, SEAD-evasion
scoot, EWR grouping, band caps and the AWACS fold-in. Grimes' script is MIST-dependent and
unlicensed. Take the ideas and the numbers; leave the code.

## 5. TrainingSams — small, usable, optional

`DCS-miscScripts/TrainingSams/trainingSams.lua`, ~120 lines. Tracks every missile in flight;
when one closes inside `removalDist` (default 300 m, MP-safe) of its original target it is
deleted via `Object.destroy()` and the player is told they were hit. Settings: removal method
(destroy vs a 5 kg explosion), removal distance, AI-shots-only, players-only.

For a campaign generator this is a training mode, not a campaign feature — it destroys attrition,
which is the point of a turn. It is a plausible **default-off plugin** for a squadron BFM/SAM
evasion night: fly a real generated turn against real red air defence, learn the picture, keep
the jet. Cost is a small plugin plus a setting.

Do not copy his file (unlicensed). The mechanism is three DCS API calls and is trivially
reimplemented: catch `S_EVENT_SHOT`, poll `get3DDist(missile, target)`, destroy inside the
threshold.

## 7. SLmod — learn, do not adopt

Server-side mod: persistent per-player stats (kills, deaths, friendly fire, flight time), an
admin chat menu, auto-moderation for team-kills and collisions, chat logging, MOTD, live unit
and event export.

The stats half overlaps **§91 per-flight sortie records** — but SLmod runs as a DCS *server hook*
(`Scripts/Hooks`), outside the mission scripting sandbox. Retribution installs no server mods, so
that integration path is closed to us. We already catch `S_EVENT_SHOT` and `S_EVENT_HIT` in
`resources/plugins/base/dcs_retribution.lua` and report through the debrief channel.

Worth reading once if §91's shot/hit attribution ever proves unreliable — SLmod has had a decade
of multiplayer edge cases beaten out of it. Nothing to take today.
