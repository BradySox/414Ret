Three ways out of the dialog maze

Retribution's interface is a 2016 Qt app wearing a hand-written stylesheet, with a modern web map bolted into the middle of it. Everything we've done so far has been repair work. This is a pitch for three different redesigns — pick a direction, and the repairs stop being repairs.

~90 screens 36 dialogs 439 settings controls 29,494 lines of UI code
The problem

Where it stands

Not opinions. Every point below is something in the code right now.

Retribution is two applications glued together. A PyQt desktop app owns the window, the menus, the sidebar and every single dialog. A React web app owns the map, and is embedded as one pane of a splitter inside that window. The two were designed years apart by different hands, and they have never shared a colour, a font size, or a spacing rule.

The result isn't ugly so much as unowned. There's no design system on either side, so every fix is a local patch, and the patches don't add up to a look.

Seven things that are actually broken

  • Modality
    Everything you do is a modal dialog on top of the map. There are 36 dialog classes. Right-clicking a target on the web map doesn't open anything in the browser — it POSTs to /qt/create-package/… so the Qt app can throw a modal over the top. The moment you edit a flight, the map you were reading it against is gone.
  • Navigation
    Four competing navigation systems, none of them complete. A menubar, three separate toolbars, a row of buttons in the status strip, and the ATO tree. Settings lives in a toolbar; Air Wing lives in the status strip; base details are only reachable by clicking the map. Nothing tells you which is which.
  • Hierarchy
    Discord, Github and Ukraine sit at the same visual weight as “Take off”. They are a peer toolbar to campaign actions. The single most important control in the app — the one that generates and launches the mission — is one grey gradient button among sixteen.
  • Fit
    Dialogs did not fit on real monitors, so we wrote a global clamp. qt_ui/screenfit.py is an app-wide event filter that shrinks and repositions every dialog as it opens, because only 2 of 34 ever consulted the screen size. That's a workaround for a layout system that was never sized.
  • Tokens
    The styling is hardcoded hex, in two unrelated palettes. Qt: a 711-line stylesheet of literal colours and gradients with no variables and 139 fixed px rules that fight DPI scaling. Web: no custom properties at all outside the map vectors — seven near-identical greys, two different border colours for the same role, four base font sizes.
  • Layout
    The web client has no layout — only corners. Its root element has zero CSS rules. The ribbon, events feed, legend and layers panel are absolutely positioned into four corners and kept apart by magic numbers and one hand-bumped z-index. There is not a single media query in the entire client.
  • Rot
    Deleted features are still styled. The status ribbon's stylesheet is 386 lines; roughly two-thirds of it styles a posture chip and a campaign-phase panel whose markup was removed months ago. The browser tab still says “React Redux App”.
The pattern. Every one of those is a symptom of the same missing thing: nobody ever decided what this application looks like. That's the decision this document is asking for — not a stylesheet.

1Direction one · restyle

Sortie

Change nothing about how the app works. Give it a design system and let every screen inherit it at once.

The layout stays exactly as it is: menubar, toolbar, status strip, ATO on the left, map in the middle, log at the bottom, dialogs on top. What changes is that the 711-line stylesheet and the web client's scattered hexes are both replaced by one token file — colour, spacing, type scale, border radius, elevation — from which the Qt stylesheet is generated and the web CSS is written.

That single move fixes the thing you notice most: the two halves of the app finally look like one program. The gradients go. The type gets a scale. The toolbar loses the social links. And the one button that matters becomes the one button that's coloured.

2Direction two · restructure

Command Deck

Kill the modal. The map never leaves the screen, and what you selected explains itself in a panel beside it.

This is the direction that changes how the app feels rather than how it looks. The insight is that almost nothing in Retribution is genuinely modal — you're not being asked a blocking question, you're inspecting and adjusting a thing you picked on the map. So the 36 dialogs collapse into one persistent inspector on the right that changes contents with your selection, and a mode rail on the left that replaces the toolbar/menubar/status-button scramble.

Click a SAM site: the inspector shows it. Click a flight: the inspector shows General, Payload, Waypoints and DTC as sections you scroll, with the flight's route still drawn on the map next to you. Drag a waypoint and watch the fuel figure move. Today that is literally impossible, because the dialog is covering the map.

Crucially this is incremental. The inspector can host one converted dialog at a time; everything not yet converted keeps opening as a modal exactly as it does now. There is no big-bang cutover.

3Direction three · replatform

Single Surface

Stop maintaining two applications. The web client becomes the whole interface; Qt keeps the window and the file dialogs.

Retribution has been drifting this way for two years without anyone deciding to. The map is already a web app. The layers panel, the campaign ribbon, the SITREP, the victory checklist, the events feed, the minefield and downed-pilot overlays — every one of those was built web-side. The server already publishes the game as JSON over HTTP and pushes deltas over a WebSocket. There is even an Electron wrapper sitting in the repo, unused.

What's missing is only the write half. Today the browser can't create a package — it POSTs to /qt/create-package/… and asks the desktop app to open a dialog. Direction 3 is the decision to finish the job: build the write endpoints, move the remaining screens into React, and let the Qt shell shrink to a launcher.

The payoff is the one nothing else can offer. Planning moves to a second monitor, a laptop or a tablet on the desk while DCS runs fullscreen — and because it's just a page on the local network, others in the squadron can watch the campaign map during a brief without touching your machine.

They are not exclusive

Direction 1 is a prerequisite for both of the others — the token system is the same work either way. Direction 2 and Direction 3 are the real fork in the road, and they differ mostly in where the inspector gets built: in Qt, or in React. The honest sequencing is:

If you want…Do this
A visibly better app soon, with almost no riskDirection 1, then stop and reassess
The biggest change to how planning feels, staying on QtDirection 1 → Direction 2
To end the two-application problem for goodDirection 1 → Direction 3 steps 2–6
What I need from you

React to these, don't pick one

You said you don't know what you want yet — that's fine, and it's why this is three directions rather than three mockups of the same thing. The useful reaction isn't “option 2”; it's which parts made you feel something.

  1. Which mockup did you want to keep looking at? Ignore the labels and the cost columns. First reaction only.
  2. Is losing the map behind a dialog actually annoying you, or have you stopped noticing? If it doesn't bother you, Direction 2's whole premise is wrong and we should say so now.
  3. Does planning on a second screen or a tablet matter to you? That's the one thing only Direction 3 buys, and it's expensive. If it's a shrug, Direction 3 drops out.
  4. The three palettes are deliberately different — warm dark, cold dark, light. Any of them wrong on sight? That's cheap to change now and expensive later.
  5. Anything here you'd actively defend? The ATO sidebar, the toolbar, the current colours — if something works for you, I'd rather know before redesigning around it.
